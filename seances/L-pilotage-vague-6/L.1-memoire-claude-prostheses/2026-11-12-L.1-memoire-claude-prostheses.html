RÉCUPÉRER

Le dernier maillon de la lignée : Claire renommée, devenue une « salle virtuelle » de collègues IA (des prothèses) où Yanis joue tous les rôles de Scrum, puis une usine à documents MRD → Code poncée séance après séance. C'est là que sont nés les outils et la méthode de pilotage qu'il utilise encore.

1 · Déclencheur

Le 25/05, Yanis veut que chaque session Claude démarre avec le bon contexte, sans tout recharger. Le premier commit crée 3 « agents » (indie-dev, pm, dev-anthropic). Chacun a un script qui compresse ses sources en ~3 000 tokens : l'écosystème de Claire, le vault, les audits des repos Anthropic [1] [2]. Ce n'est pas un nouveau projet : le 01/06, Yanis écrit que « Claire » est l'ancien nom de claude-prothèse [3]. L'hypothèse d'un départ inspiré d'alirezarezvani ne tient pas : ce repo n'apparaît que le lendemain, comme un audit qui « valide » la vision [5].

2 · Objectif

Une vision dictée le 26/05 : un tableau de bord par projet avec tous les documents qui mènent de l'intention au logiciel, reliés par un « linéage » où chaque document part du précédent. Chaque document porte sa « volatilité » : quand le relire, quand le réécrire. Une « spec day » par projet remplit tous ces documents. Une « simulation de collègues IA (prothèses) » complète le tout, mais « c'est moi qui joue chacun des rôles ». Bénéfice attendu : « n'avoir que des choses claires et simples à faire chaque jour », pour du logiciel comme pour un pâtissier [4].

C. Ce que les traces ajoutent au souvenir

  • Claire et claude-prostheses ne font qu'un. Les fiches précédentes les présentent comme deux étapes. Yanis l'a corrigé lui-même le 01/06, dans une décision écrite (DEC-16) : Claire est l'ancien nom, « avant que Yanis sache nommer les choses ». Elle n'est pas un projet sur lequel tester l'outil [3].
  • Le ledger est plus ancien que metrics/sessions.csv. Le registre Ops naît le 30/05, passe en CSV le 07/06, et c'est lui que sert ops_ledger.py. Le sessions.csv de fin-session date du 09/06. L'hypothèse de K.2 est donc inversée : si l'un descend de l'autre, c'est sessions.csv qui suit le ledger (interprétation de Claude, confiance moyenne) [11] [22].
  • Les juges R-gate sont nés ici, le 03/06, et ce ne sont pas les personas. Les personas sont les 4 rôles du 26/05 : ils produisent. Les juges du 03/06 sont des sous-agents anonymes (défenseur, attaquant, neutre) : ils évaluent. L'idée « plusieurs avis » de la lignée a donc deux branches dans ce repo [7] [12].
  • La méthode de cette reprise vient de juin. Séances nommées par lettres (B → AZ), kernels de lancement, contrats parallèles en worktree, intégration par vagues, ledger avec ctx_close et violations : tout cela existe dès le sprint 15. La reprise de novembre le réapplique, elle ne l'invente pas [14] [16] [20].
  • Deux « Sprint 4 » : deux numérotations successives. Le 26/05, les sprints 1 → 4 sont un sprint par rôle. Le 27/05, la « spirale Scrum » repart à 1 (« Sprint 1 Dispatcher ») et continue jusqu'au sprint 15 ; le dossier sprints/ ne suit que cette 2ᵉ série. Yanis ne s'en souvenait pas [7] [24] [23].
  • Le plugin aux hooks coûteux, c'était planning-with-files. Yanis se souvient d'un plugin qui consommait beaucoup de tokens sans qu'il le sache. pwf/findings.md le chiffre : ~890 000 tokens par session avec les hooks par défaut, ~7 000 avec le seul hook Stop. D'où la règle « /debut-session = skill manuel, pas un hook ». Son propre hook PreToolUse (29/05) vérifiait, avant chaque skill, que la cérémonie précédente était faite [8] [9] [23].
  • E a absorbé le projet, par choix. À partir du 01/06, les rôles et les cérémonies deviennent des outils forgés dans la chaîne (le « quatuor » du 23/06 : sprint-planning, sprint-review, retrospective, gate-dod). Yanis le confirme : la mécanique Scrum a été mise de côté pour se concentrer sur E, sous un forfait à 90 € « juste juste ». Le README, lui, décrit encore la salle virtuelle de fin mai [16] [23].
  • Un mois très dense. 369 commits, environ 70 séances, dont 68 commits le seul 30/05 ; puis un seul commit entre le 24/06 et le 12/11 [6].

6 · Ce qui déclenchait l'usage

  • Prévu : Un nouveau projet démarre → une « spec day » remplit tous les documents ; les prothèses-rôles tiennent les cérémonies ; le framework est copié dans chaque projet (project_scaffold.py) [4] [9]
  • Réel : Le seul projet traité est claude-prothèse lui-même (MRD « racine », n=1). Le premier usage sur un projet externe reste un objectif (T1) [18]. C'était voulu : Yanis construisait l'outil et voulait le terminer avant de l'utiliser sur un projet annexe (app, site, création de contenu) [23]. Une séance démarrait par /debut-session sur le dernier kernel et finissait par /goedel et une ligne au ledger [11] [16]
  • Réel aujourd'hui : Clôture d'une séance de reprise → ops_ledger.py append. Ouverture → /debut-session. Le reste ne sert plus [19] [20]

7 · Où je me suis arrêté

Le 23/06, la séance AZ ferme le dernier maillon : les gabarits MRD → Code existent tous. Le gabarit Code reste « en ponçage » tant que le SRD parent n'est pas verrouillé. Le kernel AZ laisse deux options : verrouiller le SRD ou compléter le ledger [16]. Ce même kernel note un sur-investissement : contexte à 92 %, 8,68 $, interrompu par « qu'est-ce qu'on fout là » [16]. La raison de l'arrêt est un voyage : Yanis partait le 01/07, une semaine plus tard, et voulait terminer la chaîne avant [23]. Bilan : la structure est terminée (les 5 gabarits existent), le verrouillage ne l'est pas (SRD non verrouillé, donc Code « en ponçage ») ; il restait une ou deux séances. Le statut exact de chaque gabarit n'a pas été lu [16].
